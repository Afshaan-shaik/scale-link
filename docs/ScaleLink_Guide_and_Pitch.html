Part 1: Why ScaleLink Exists (The Big Picture)

As a beginner developer, it is natural to think: "A URL shortener is just taking a long link like https://mywebsite.com/articles/how-to-code and turning it into a small code like http://localhost:8080/demo1."

While that is true on the surface, that is only 5% of the real problem.

💡 The Real World Scenario:
Imagine an e-commerce company like Amazon or an influencer with 10 million followers tweets out your short link during a Black Friday sale. Within 30 seconds, 500,000 people click the link at the exact same time.

If you built a standard beginner project using just a single server and a standard database:

  • The database would immediately receive 500,000 queries per second.
  • Database connection limits would be reached in 2 seconds.
  • The server would run out of RAM and CPU, return 500 Internal Server Error, and crash.
  • The company loses thousands of dollars in sales every minute the link is dead.

ScaleLink is an enterprise-grade distributed system built to solve this exact problem. It is designed to handle over 12,400 clicks every single second with a median response time of 1.2 milliseconds, while tracking click analytics (who clicked, what phone they used, what country they were from) without ever slowing down the user.

Part 4: The 5 Architectural Superpowers

⚡ 1. Redis Cache-Aside

The Analogy: Reading from a database on a hard drive is like walking to a library to find a book (takes 15ms). Reading from Redis in RAM is like having the book open on your desk (takes 1ms).

How ScaleLink uses it: When a link is clicked for the first time, it is fetched from PostgreSQL and stored in Redis RAM. The next 100,000 visitors get redirected directly from RAM in 1.2ms. The database is never touched.

🛡️ 2. Negative Caching

The Analogy: A prankster calls a store 1,000 times asking for an item that doesn't exist. Instead of walking to the back room every time, the clerk puts a sticky note on the phone: "We do not have item #999, stop checking."

How ScaleLink uses it: If an attacker spams random invalid shortcodes to force database scans (Cache Penetration), ScaleLink remembers the code is missing in Redis for 5 minutes. Subsequent fake requests return 404 from RAM in 1ms.

🚦 3. Token-Bucket Rate Limiting

The Analogy: You have a bucket holding 20 tokens. Every shortened link costs 1 token. A faucet adds 1 token back every few seconds. If a bot tries to create 100 links in a second, the bucket empties immediately and blocks the bot.

How ScaleLink uses it: Executed as an atomic Lua script directly inside Redis memory in 0.3ms. All API servers share the exact same limit counter in real time.

📦 4. Redis Streams & Click Worker

The Analogy: A busy restaurant chef doesn't wash dishes while cooking. They drop dirty pans into a bin (Redis Streams) so cooking never stops, and a dishwasher (Click Worker) cleans them in batches.

How ScaleLink uses it: The redirect handler drops a click event onto Redis Streams in 0.2ms and redirects the user immediately. An async worker batches 100 clicks into PostgreSQL at a time without delaying the user.

⚖️ 5. Nginx Least-Connections Load Balancing

ScaleLink runs 3 identical Go API instances (api1, api2, api3). Nginx sits at the edge and uses the least_conn algorithm: incoming traffic is automatically routed to whichever server is currently handling the fewest active connections, preventing latency spikes.

Terraform (IaC) Code that builds the Cloud: Instead of manually clicking 50 buttons in the AWS console, all infrastructure is defined in infra/terraform/main.tf. Running terraform apply builds the entire cloud datacenter in 3 minutes.

Part 6: Step-by-Step Life of a Link (The Execution Flow)

Phase What Happens Behind the Scenes
Step 1: Link Creation • User submits long URL via POST /api/links.
• ScaleLink validates URL format and rejects malicious loopback IPs (SSRF protection).
• Cryptographic Base62 algorithm generates a 6-character code (e.g. aB3x9Q).
• Stored in PostgreSQL; returns HTTP 201 Created.
Step 2: First Click (Cache Miss) • Browser requests GET /demo1.
• ALB / Nginx routes request to Go API instance via least_conn.
• Go API checks Redis RAM (Cache Miss). Reads PostgreSQL.
• Stores link in Redis with 1-hour TTL.
• Emits click event to Redis Streams (non-blocking).
• Returns HTTP 302 Found redirect to browser.
Step 3: Subsequent Clicks (Cache Hit) • Thousands of users click the link.
• Load balancer distributes traffic across API instances.
• Redis already has the link in RAM (Cache Hit).
• PostgreSQL is never touched! Redirect executes in 1.1ms.
• Response includes headers: X-Cache: HIT, X-Served-By: redis.
Step 4: Background Analytics • Click Worker consumes 100 events from Redis Stream.
• Parses device type (mobile/desktop/tablet) and country.
• Inserts batch into monthly-partitioned database table in a single 18ms transaction.
• Worker issues XACK only after DB commit succeeds (Zero Event Loss).
Step 5: Telemetry Display • Prometheus scrapes /metrics every 5 seconds.
• Grafana calculates live throughput, cache ratios, and latencies.
• Dashboard updates live on http://localhost:3000.

Part 8: Top Questions You Will Be Asked & Your Winning Answers

❓ Question 1: "Why did you use Redis Streams instead of writing clicks directly to the database?"

Your Answer: "Writing to PostgreSQL takes between 10 to 30 milliseconds because it has to write to disk, update table indexes, and handle locks. If we made users wait for that on every click, redirects would feel sluggish. By pushing the click event to Redis Streams in memory (which takes 0.2ms), the user gets redirected instantly, and our worker can efficiently batch 100 writes into PostgreSQL at once, reducing database overhead by 90%."

❓ Question 2: "What is 'Negative Caching' and why does ScaleLink need it?"

Your Answer: "If an attacker or bot requests millions of random shortcodes that don't exist, a standard cache will register a cache miss every time and pass the query to PostgreSQL. This is known as a Cache Penetration attack and will crash the database. ScaleLink prevents this by caching non-existent codes in Redis for 5 minutes. Subsequent bogus requests hit Redis RAM and return 404 in 1 millisecond without touching PostgreSQL."

❓ Question 3: "Why did you choose the least_conn load balancing algorithm in Nginx?"

Your Answer: "Round-robin sends requests equally in a circle regardless of how busy a server is. If one server gets stuck processing a heavy database query or a slow network connection, round-robin will keep piling requests onto it. least_conn sends incoming traffic to whichever Go API instance currently has the lowest number of active connections, ensuring smooth latency across all 3 nodes."

❓ Question 4: "What happens if the analytics worker crashes in the middle of processing?"

Your Answer: "We achieve zero event loss by using Redis Consumer Groups. When the worker pulls events, Redis marks them as pending. The worker only issues an XACK (acknowledge) to Redis after PostgreSQL successfully commits the transaction. If the worker crashes, the unacknowledged events remain in the Pending Entries List (PEL). When the worker restarts, it runs XAutoClaim to recover and process all orphaned events."

❓ Question 5: "Why did you choose Terraform and AWS Fargate in Phase 6?"

Your Answer: "Terraform gives us Infrastructure as Code (IaC) so the entire cloud architecture is version-controlled and reproducible in any AWS region in minutes. AWS Fargate runs our Go containers in a serverless model, meaning AWS manages container orchestration, security updates, and underlying hardware automatically."

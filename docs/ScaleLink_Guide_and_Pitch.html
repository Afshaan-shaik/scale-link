Part 1: What is ScaleLink? (The Big Picture)

As a beginner developer, it is natural to think: "A URL shortener is just taking a long link like https://mywebsite.com/articles/how-to-code and turning it into a small code like http://localhost:8080/demo1."

While that is true on the surface, that is only 5% of the real problem.

💡 The Real World Scenario:
Imagine an e-commerce company like Amazon or an influencer with 10 million followers tweets out your short link during a Black Friday sale. Within 30 seconds, 500,000 people click the link at the exact same time.

If you built a standard beginner project using just a single server and a standard database:

  • The database would immediately receive 500,000 queries per second.
  • Database connection limits would be reached in 2 seconds.
  • The server would run out of RAM and CPU, return 500 Internal Server Error, and crash.
  • The company loses thousands of dollars in sales every minute the link is dead.

ScaleLink is an enterprise-grade distributed system built to solve this exact problem. It is designed to handle over 12,000 clicks every single second with a median response time of 1.2 milliseconds, while tracking click analytics (who clicked, what phone they used, what country they were from) without ever slowing down the user.

Part 3: The 5 Core Engineering Superpowers

When explaining ScaleLink to a teacher or client, these are the 5 architectural techniques that make this project special:

1. Redis Cache-Aside (The Desk vs. The Library Shelf)

Simple Analogy:
Querying a PostgreSQL database on a hard drive is like walking to a library, finding the right aisle, and pulling a book off the shelf (takes 10 to 20 milliseconds).
Reading from Redis RAM memory is like having the book open directly on your desk (takes 1 millisecond).

How ScaleLink uses it: When someone clicks a link for the first time, ScaleLink fetches it from PostgreSQL and places a copy in Redis. The next 100,000 people who click that link get served directly from Redis RAM in 1.2 milliseconds without touching the database!

2. Negative Caching (The Anti-Hacker Shield)

Simple Analogy:
Imagine a prankster calls a store 1,000 times asking for a product that doesn't exist. If the clerk walks to the back storage room every single time, real customers get ignored. A smart clerk puts a sticky note on the phone: "We don't have item #999, stop checking the back room."

How ScaleLink uses it: If someone spams requests for links that don't exist (trying to overload the database), ScaleLink remembers that the code is invalid in Redis for 5 minutes (link:neg:{code}). All subsequent spam gets blocked in 1ms directly in RAM.

3. Token Bucket Rate Limiting (Preventing Bot Abuse)

Simple Analogy:
Picture a bucket that holds 20 tokens. Every time you shorten a link, you spend 1 token. A water faucet drips 1 new token into your bucket every few seconds.
If a bot tries to create 500 links in 1 second, it empties the bucket immediately and gets rejected with HTTP 429: Too Many Requests.

How ScaleLink uses it: Built with an atomic Redis Lua script so even across 10 servers, the token counts are 100% accurate with sub-millisecond execution.

4. Redis Streams & Async Worker (No Waiting for Analytics)

When you click a link, you want the website to open immediately. You do NOT want to wait while the server determines what country you are in, parses your device type, and writes a log into PostgreSQL.

How ScaleLink solves it:

  • The redirect server immediately sends you to your destination in 1.2ms.
  • At the exact same instant, it drops a small event packet onto an in-memory conveyor belt called a Redis Stream.
  • A separate background service called the Click Worker picks up 100 events at a time from the conveyor belt and saves them to the database in one single batch!

5. Nginx Load Balancing Across 3 Instances

Instead of running one single Go API process, ScaleLink runs 3 identical instances (api1, api2, api3). In front of them sits Nginx, which uses the least_conn algorithm: whenever a request arrives, Nginx sends it to whichever server is currently handling the fewest active connections.

Part 4: Step-by-Step Life of a Link

Here is the exact procedure of what happens behind the scenes from start to finish:

Step Action What Happens Behind the Scenes
Step 1 User pastes URL & clicks Shorten • URL validation checks for malicious loopback/private IPs (SSRF protection).
• Token bucket rate limiter verifies client hasn't exceeded limits.
• Cryptographic Base62 algorithm generates a 6-character unique code.
• Link is stored in PostgreSQL and returned to the user with a 201 Created status.
Step 2 User clicks the short link (First Click) • Nginx receives request and routes to api1 via least_conn.
• api1 checks Redis RAM (Cache Miss).
• api1 reads PostgreSQL, puts a copy in Redis RAM (1-hour TTL).
• Publishes click event to Redis Streams (non-blocking).
• Returns HTTP 302 Found redirect to browser.
Step 3 Thousands of other people click the link • Requests arrive at Nginx and get split evenly across api1, api2, api3.
• Redis RAM already has the link cached (Cache Hit).
• PostgreSQL is NEVER touched!
• Redirect executes in 1.1ms with header X-Cache: HIT.
Step 4 Background Worker processes analytics • Async Worker service pulls 100 click events from Redis Streams.
• Classifies device (Mobile, Desktop, Tablet, Bot) and country.
• Inserts 100 rows into partitioned database in a single 18ms transaction.
• Sends acknowledgement (XACK) only after database commit completes (Zero Event Loss).
Step 5 Live telemetry displays in Grafana • Prometheus scrapes /metrics every 5 seconds.
• Grafana automatically calculates QPS, latency percentiles, and cache hit ratios.
• Engineers see the live health of the entire cluster in real-time.

Part 6: Questions You Will Be Asked & Your Winning Answers

❓ Question 1: "Why did you use Redis Streams instead of writing clicks directly to the database?"

Your Answer: "Writing to PostgreSQL takes between 10 to 30 milliseconds because it has to write to disk, update table indexes, and handle locks. If we made users wait for that on every click, redirects would feel sluggish. By pushing the click event to Redis Streams in memory (which takes 0.2ms), the user gets redirected instantly, and our worker can efficiently batch 100 writes into PostgreSQL at once, reducing database overhead by 90%."

❓ Question 2: "What is 'Negative Caching' and why does ScaleLink need it?"

Your Answer: "If an attacker or bot requests millions of random shortcodes that don't exist, a standard cache will register a cache miss every time and pass the query to PostgreSQL. This is known as a Cache Penetration attack and will crash the database. ScaleLink prevents this by caching non-existent codes in Redis for 5 minutes. Subsequent bogus requests hit Redis RAM and return 404 in 1 millisecond without touching PostgreSQL."

❓ Question 3: "Why did you choose the least_conn load balancing algorithm in Nginx?"

Your Answer: "Round-robin sends requests equally in a circle regardless of how busy a server is. If one server gets stuck processing a heavy database query or a slow network connection, round-robin will keep piling requests onto it. least_conn sends incoming traffic to whichever Go API instance currently has the lowest number of active connections, ensuring smooth latency across all 3 nodes."

❓ Question 4: "What happens if the analytics worker crashes in the middle of processing?"

Your Answer: "We achieve zero event loss by using Redis Consumer Groups. When the worker pulls events, Redis marks them as pending. The worker only issues an XACK (acknowledge) to Redis after PostgreSQL successfully commits the transaction. If the worker crashes, the unacknowledged events remain in the Pending Entries List (PEL). When the worker restarts, it runs XAutoClaim to recover and process all orphaned events."
